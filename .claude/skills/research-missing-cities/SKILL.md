Исследуй все города из `travel-knowledge-base/uk/london-day-trips.md`, у которых ещё нет собственной статьи, и для каждого создай готовый к мерджу PR. Работай строго по фазам и **по одному городу за итерацию** — полностью завершай цикл (исследование → ревью → исправления) для одного города, прежде чем переходить к следующему.

Опциональный `$ARGUMENTS` ограничивает объём работы: это может быть число (обработать не более N городов) или название конкретного города (обработать только его). Если `$ARGUMENTS` пуст — обрабатывай все недостающие города.

## Фаза 0: Сбор списка недостающих городов

1. Прочитай `travel-knowledge-base/uk/london-day-trips.md`. В сводной таблице («Направление») найди строки, где название города — **обычный текст, а не markdown-ссылка** `[Город](файл.md)`. Это кандидаты на исследование.

2. **Отсей ложные кандидаты — таблица часто устаревшая, статья может уже существовать.** Для каждого кандидата проверь и **исключи** его, если выполняется хотя бы одно:
   - Статья уже есть: найди файл по русскому названию и по латинской транслитерации в `travel-knowledge-base/uk/` (`ls travel-knowledge-base/uk/` + `Glob`/`Grep`; например `Норидж` → `норидж.md`/`norwich.md`, `Челтнем` → `челтнем.md`). Если соответствующий файл существует — пропусти город (он уже исследован, ему просто не проставлена ссылка в таблице).
   - Уже есть открытый PR на этот город: `gh pr list --state open --json number,title,headRefName`. Если в заголовке/ветке фигурирует этот город — пропусти (не плоди дубликаты; в репозитории такое уже случалось).

3. Сформируй финальный список городов к обработке. Применени к нему ограничение из `$ARGUMENTS` (число или конкретный город), если оно задано.

4. Выведи пользователю итоговый список с количеством и заведи трекер прогресса через **TodoWrite** (по одному пункту на город: «<Город>: research → review → fix»). Если список пуст — сообщи, что недостающих городов нет, и заверши работу.

## Фаза 1: Исследование города (→ PR)

Для текущего города:

1. Определи slug для статьи (он же `$ARGUMENTS` для команды research.city и имя файла). Держись существующих соглашений репозитория; при сомнении используй латинскую kebab-case транслитерацию. Slug должен быть уникальным и не конфликтовать с существующими файлами/ветками.

2. Прочитай `.claude/commands/research.city.md` и **выполни все его инструкции** с `$ARGUMENTS` = выбранный slug города. Результатом должны быть: новая ветка `research/<slug>`, статья `travel-knowledge-base/uk/<slug>.md`, чеклист, обновлённая навигация и **созданный PR** (`gh pr create`).

3. Зафиксируй **номер созданного PR**: `gh pr list --head research/<slug> --state open --json number,url` (или возьми из вывода `gh pr create`). Этот номер используется в фазах 2 и 3.

## Фаза 2: Ревью PR (→ комментарий)

1. Прочитай `.claude/commands/review.md` и применяй его критерии проверки (соответствие `structure.md` и шаблонам, консистентность навигации, содержание/здравый смысл, форматирование).

2. **Важно: ревьюй только PR, созданный в Фазе 1** (по его номеру), а не все открытые PR — иначе на каждой итерации будут повторно перепроверяться уже обработанные города. Шаги ревью для этого PR:
   - `gh pr diff <номер>` и `gh pr view <номер>`;
   - прочитай целиком затронутые файлы (не только diff).

3. Оставь итог ревью комментарием в PR:
   - если всё корректно — `gh pr review <номер> --approve --body "<краткий комментарий>"`;
   - если есть замечания — `gh pr review <номер> --request-changes --body "<список замечаний по категориям, с указанием файла и места>"`.

   Соблюдай ограничения review.md: **никогда не мёржи PR** и не пуш в чужие ветки (ветка `research/<slug>` — наша, в неё пушить можно).

## Фаза 3: Исправление важных недоработок (→ пуш + комментарий)

1. Если в Фазе 2 был `--approve` без существенных замечаний — пропусти правки и переходи к шагу 4 (отметь, что исправления не требовались).

2. По замечаниям ревью исправь **важные** недоработки в файлах ветки `research/<slug>` (фактические ошибки, нарушения шаблона/структуры, битая навигация, пустые разделы, сломанные таблицы, GDPR). Косметику делай только если она быстрая; не уходи в бесконечную полировку.

3. Закоммить и запушь изменения в ту же ветку явными командами:
   ```
   git add <изменённые файлы>
   git commit -m "Review fixes: <slug>"
   git push
   ```

4. Оставь в PR комментарий о сделанных изменениях: `gh pr comment <номер> --body "<что исправлено по пунктам ревью; если правок не было — почему>"`.

5. Отметь город завершённым в **TodoWrite** и переходи к следующему городу (вернись к Фазе 1).

## Фаза 4: Финал

Когда все города из списка обработаны, выведи пользователю итоговую сводку — список PR, готовых к мерджу, с номерами, ссылками и одной строкой статуса по каждому (`gh pr list --state open --json number,title,url`). Это и есть результат работы скилла.

## Гарантии и ограничения

- **Один город — один полный цикл.** Не запускай исследование следующего города, пока для текущего не пройдены все три фазы.
- **Не создавай дубликаты.** Перед исследованием всегда перепроверяй, что для города нет существующей статьи и нет открытого PR.
- **Никогда не мёржи PR** и не закрывай чужие PR.
- Пушь правки только в собственные ветки `research/<slug>`.
- Если `research.city` или `review` для города падает с ошибкой — зафиксируй проблему в TodoWrite, не прерывай весь цикл, переходи к следующему городу и сообщи об этом в финальной сводке.
